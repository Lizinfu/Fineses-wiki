# 世界观图书馆 Wiki 需求基线

> 文档用途：统一产品、世界观策划、内容编辑、前端、后端与运维人员对 Wiki 的理解，并作为后续设计、开发、验收和迭代的共同依据。
>
> 当前状态：已完成 Hugo + GitHub Pages 初版界面、内容模型/关系/时间线校验、Pagefind 搜索、媒体与站点输出检查，以及 PR 中的 Playwright/axe 浏览器检查。本文件描述的是完整 Wiki 的目标形态和验收基线；当前实际操作以根目录 `README.md`、`docs/` 专题规范和 `.github/workflows/` 为准。

---

## 1. 项目背景

本项目是一个用于收录、整理和展示原创游戏世界观资料的公开 Wiki 网站。

世界观规模辽阔，包含多个具有不同语言、历史、政体、信仰、生态与社会结构的国家和文化区域。内容体量将持续增长，资料类型包括但不限于：

- 国家、政权与行政区；
- 人物及人物关系；
- 组织、公司、军队、宗教与学术机构；
- 历史时代、事件、战争、灾害与制度变迁；
- 地区、城市、地理环境、生态区和自然现象；
- 物种、疾病与生物群落；
- 技术、宗教、语言、哲学、法律、经济等概念；
- 物品、武器、材料、载具、艺术品和遗物；
- 报告、信件、法令、新闻、访谈、残片等世界内文献。

Wiki 本身同时属于世界观的一部分。网站被设定为一座沉寂多年后重新被发现的图书馆，在信息时代建立的互联网馆藏界面。它不是单纯模仿纸质古籍的复古网页，而是一个由古老机构建立、经过现代化改造的高功能信息系统。

网站应在沉浸式叙事与现代信息产品之间取得平衡：

- 用户首先能够快速找到、理解和交叉阅读资料；
- 图书馆设定通过馆藏编号、资料来源、可信度、复核记录、馆员批注等细节体现；
- 任何装饰和叙事效果都不能妨碍可读性、检索和移动端使用。

## 2. 项目目标

### 2.1 核心目标

1. 建立一个可持续扩展的世界观资料库。
2. 让读者能够通过目录、分类、搜索和关联条目理解世界观。
3. 让策划与内容编辑能够使用 Markdown 独立新增和修改条目。
4. 保证国家、人物、事件等资料只维护一个权威版本，避免重复和互相矛盾。
5. 让前端视觉和交互可以持续升级，而不需要反复重构内容文件。
6. 通过 Git、自动构建和审核流程保留清晰的修订历史。
7. 将 Wiki 塑造成世界观叙事的一部分，而不是脱离作品的普通百科网站。

### 2.2 非目标

当前项目不以以下能力为首要目标：

- 用户注册与个人账号；
- 公开评论区；
- 类似传统 MediaWiki 的浏览器内复杂编辑器；
- 真实的世界内机密访问控制；
- 实时多人协作编辑；
- 动态服务端数据库；
- 大规模社交功能。

如未来确有需求，应单独立项评估，不应在现有静态站点中临时拼接。

## 3. 目标用户

### 3.1 普通读者

需求：

- 快速了解某个国家、人物或概念；
- 沿着正文中的引用继续阅读；
- 搜索名称、别名、馆藏编号或正文关键词；
- 在手机、平板和桌面端稳定浏览。

### 3.2 深度世界观读者

需求：

- 按时代、文化圈、地域、主题等维度探索资料；
- 查看事件参与者、人物所属组织、国家关系和文献来源；
- 理解互相冲突或可靠性不同的世界内记录；
- 使用时间线、地图或关系网络进行系统性阅读。

### 3.3 世界观策划与内容编辑

需求：

- 使用标准模板创建条目；
- 不修改前端代码即可录入正文、图片、分类和关系；
- 在提交前本地预览；
- 能够发现无效链接、重复 ID、错误分类和缺失字段；
- 可以追溯谁在何时修改了什么内容。

### 3.4 前端与体验设计人员

需求：

- 内容结构稳定、字段语义明确；
- 组件可以复用，不必为每个条目单独制作页面；
- 设计系统与内容数据分离；
- 可以在不修改正文文件的情况下迭代视觉与交互。

### 3.5 技术维护与运维人员

需求：

- 构建过程可重复；
- 主分支可自动部署；
- 错误能够在合并前被发现；
- 版本可回滚；
- 依赖、构建命令和目录职责清晰。

## 4. 产品范围与主要板块

### 4.1 用户侧一级导航

建议一级导航长期控制在 6—7 个入口：

1. **阅览大厅**：首页、推荐馆藏、最近修订、入门阅读路径。
2. **国家与地区**：国家、政权、行政区、城市、地理区域和地图。
3. **人物与组织**：人物、政府、公司、军队、宗教、学术机构和派系。
4. **历史与年代**：时代、事件、战争、灾害、迁徙和制度变化。
5. **概念与档案**：技术、信仰、语言、法律、材料、物品和原始文献。
6. **生态与物种**：生态区、物种、疾病和自然现象。
7. **检索中心**：全文搜索、分类筛选与高级浏览。

后台内容目录可以更细，但用户导航不应把所有实体类型平铺成十几个同级按钮。

### 4.2 实体类型

完整版本至少支持以下实体：

| 类型 | 标识建议 | 说明 |
|---|---|---|
| 国家/政权 | `nation` | 国家、城邦、联盟、历史政权 |
| 人物 | `people` | 独立人物档案 |
| 历史事件 | `event` | 战争、灾害、会议、改革等 |
| 历史时代 | `era` | 用于组织和解释时间段 |
| 地区 | `region` | 大陆、区域、行政区、城市等 |
| 组织 | `organization` | 政府、企业、军队、宗教、派系 |
| 概念 | `concept` | 制度、技术、宗教、语言、理论 |
| 物品 | `artifact` | 材料、武器、载具、遗物、艺术品 |
| 生态区 | `biome` | 具有统一环境特征的生态区域 |
| 物种 | `species` | 动植物、异常生命、人工生命 |
| 文献 | `record` | 报告、书信、法令、访谈、残片 |

每个实体只保存一份主档案，通过关系字段与其他实体连接。

## 5. 信息架构要求

### 5.1 内容组织原则

- 物理目录按实体类型组织，不按“当前属于哪个国家”组织。
- 人物不会因为国籍、阵营或组织变化而移动文件。
- 历史事件不会分别复制到每个参战国目录。
- 国家页面通过关系和列表自动聚合人物、事件、组织与地区。
- 大型实体可以拆分子页面；简单实体使用单页。
- 导航层级原则上不超过四层。

推荐层级：

```text
首页
└── 门户
    └── 分类或集合
        └── 实体主页面
            └── 实体子页面
```

### 5.2 页面类型

至少需要：

- 首页；
- 门户页；
- Section 列表页；
- Taxonomy 总目录；
- Taxonomy 词条页；
- 普通实体详情页；
- 大型实体主页面；
- 大型实体子页面；
- 搜索页；
- 时间线页；
- 地图页；
- 404 页面；
- 图书馆说明、访问规则和修复日志等叙事页面。

### 5.3 页面固定信息结构

实体页面建议按以下顺序展示：

1. 全局导航；
2. 面包屑；
3. 条目类型、标题与摘要；
4. 馆藏状态或可靠性提示；
5. 信息框；
6. 页面目录；
7. 正文；
8. 分类标签；
9. 关系与关联条目；
10. 世界内资料来源；
11. 修订与复核信息；
12. 同类或相邻条目。

## 6. 内容数据要求

### 6.1 稳定 ID

每个独立实体必须拥有不可重复、原则上不可修改的稳定 ID，例如：

```text
nat.lanyuan
per.luo-yan
evt.white-tide-0312
reg.north-rift
org.central-archive
con.echo-crystal
art.black-crown
rec.expedition-log-0042
```

要求：

- ID 不使用中文；
- 使用小写英文字母、数字、点号和连字符；
- 标题改名时 ID 不变；
- URL 改变时保留旧 URL 别名；
- 关系引用 ID 或 Hugo 逻辑页面路径，不依赖显示标题；
- 构建时检查重复 ID 和不存在的目标 ID。

### 6.2 基础字段

所有独立实体至少需要：

- `title`：显示标题；
- `description`：用于列表和搜索结果的摘要；
- `keywords`：别名、旧称、外文名和检索词；
- `params.id`：稳定 ID；
- `params.entity_kind`：实体类型；
- `params.library.catalog_no`：馆藏编号；
- `params.library.access_level`：世界内访问等级；
- `params.library.reliability`：世界内可信度；
- `params.library.last_reviewed`：现实中的最近复核日期。

后续应扩展：

- 正史状态；
- 剧透等级；
- 世界内年代；
- 名称变体；
- 关系数组；
- 来源文献；
- 展示图片；
- Schema 版本。

### 6.3 现实日期与世界内日期

必须分离：

- Hugo 的 `date`、`lastmod` 表示现实编辑和发布时间；
- 世界内建立、出生、发生、灭亡等日期放在专门的 `chronology` 字段；
- 世界内日期需要独立排序值，以便支持不同历法、约数和争议日期。

### 6.4 分类体系

采用受控词表，不允许无限制自由造标签。

初期 Taxonomy 至少包括：

- 文化圈；
- 历史时代；
- 主题；
- 政体类型；
- 生态类型；
- 正史状态；
- 访问级别；
- 资料可信度。

新增词条前应检查是否已有同义项，避免“军队、军方、军事组织、武装力量”等重复分类。

### 6.5 关系体系

完整版本应支持统一关系数组，例如：

- 位于；
- 隶属于；
- 首都；
- 前身/继承者；
- 成员；
- 创建者；
- 统治者；
- 盟友/敌对；
- 参与事件；
- 导致/影响；
- 持有/制造；
- 记录于；
- 一般相关。

关系应支持：

- 目标 ID；
- 起止时间；
- 可信度；
- 来源；
- 备注；
- 单向或双向属性。

系统应自动生成反向链接，避免手工在双方重复维护。

## 8. 搜索与发现要求

### 8.1 搜索字段

搜索索引至少包含：

- 标题；
- 别名、旧称和外文名；
- 摘要；
- 正文；
- 稳定 ID；
- 馆藏编号；
- 实体类型；
- 文化圈；
- 时代；
- 主题；
- 相关地名和组织名。

### 8.2 排序原则

搜索排序建议：

1. 标题完全匹配；
2. 馆藏编号或稳定 ID 完全匹配；
3. 标题开头匹配；
4. 别名匹配；
5. 标题包含；
6. 摘要和关键词；
7. 正文匹配。

### 8.3 搜索验收指标

建立固定测试词集，至少包括正式名称、简称、旧称、馆藏编号、人物所属组织、事件参与国、生态区物种等。

目标：

- 核心查询前五位命中率不低于 90%；
- 正式名称和馆藏编号应排第一；
- 分类筛选结果数量准确；
- 导航和页脚文字不进入正文搜索噪声；
- JavaScript 失效时仍可通过目录浏览内容。

## 9. 设计美学与体验要求

### 9.1 设计定位

关键词：

- 现代图书馆信息系统；
- 现实主义；
- 功能主义；
- 克制；
- 专业；
- 沉静；
- 精密；
- 有历史痕迹但不过度复古。

目标不是制作泛黄纸张风格的网站，而是表现“一座古老机构使用现代技术恢复并开放馆藏”的感觉。

### 9.2 视觉原则

- 正文可读性优先；
- 使用清晰的现代字体；
- 长文本保持合适行宽和行高；
- 用间距、层级和对齐引导视线；
- 图书馆感来自档案编号、馆藏章、状态、批注、修复记录与材质细节；
- 装饰性色彩低饱和、低干扰；
- 重要操作拥有明确对比；
- 不依赖纹理、噪点和动画表达核心信息。

### 9.3 交互原则

- 所有交互必须有明确反馈；
- 动画用于状态转换和视线引导，不用于拖延；
- 支持键盘操作；
- 焦点状态清晰；
- 搜索、筛选和目录在移动端易用；
- 动画可根据 `prefers-reduced-motion` 减弱；
- 世界内“受限”“损坏”“涂黑”效果不得隐藏真实必要信息。

### 9.4 响应式要求

至少覆盖：

- 320px 以上手机；
- 平板；
- 常见笔记本；
- 宽屏桌面。

移动端必须能完成：

- 导航；
- 搜索；
- 筛选；
- 阅读信息框；
- 浏览目录；
- 查看图片和表格。

---

## 10. 可访问性要求

- 正文与背景至少满足 WCAG AA 对比度；
- 所有交互可通过键盘完成；
- 所有新增或修改的有意义图片必须提供替代文本；既有缺失项必须由站点质量报告持续治理；
- 表单元素具有可见标签；
- 页面具有合理标题层级；
- 使用语义化 HTML；
- 当前页面、状态和错误信息可被辅助技术识别；
- 不使用仅靠颜色区分的状态；
- 不自动播放声音；
- 动态内容应使用合适的 ARIA live 区域；
- 关闭 JavaScript 后至少可以阅读正文和使用分类导航。

代表页面的 Lighthouse Accessibility 目标不低于 95。

## 11. 技术架构要求

### 11.1 当前技术栈

- 静态站点生成器：Hugo；
- 内容格式：Markdown + YAML Front Matter；
- 样式：CSS；
- 交互：原生 JavaScript，后续可按模块引入 TypeScript；
- 版本管理：Git + GitHub；
- 构建与部署：GitHub Actions；
- 托管：GitHub Pages；
- 搜索：Pagefind 静态全文索引；

### 11.2 架构原则

- 内容、模板、样式、脚本和派生数据分离；
- 不直接修改 `public/`；
- 线上产物必须由 CI 生成；
- 不把未公开剧情或内部设定放入公开构建；
- 不依赖前端密码、CSS 遮挡或隐藏元素保护秘密内容；
- 核心页面不依赖服务端数据库；
- 新模块应通过新增 Section、Schema、Archetype 和模板接入，不重构全站。

### 11.3 浏览器兼容

支持当前主流浏览器最近两个稳定大版本：

- Chrome；
- Edge；
- Firefox；
- Safari；
- iOS Safari；
- Android Chrome。

不以 Internet Explorer 为支持目标。

## 12. 性能要求

- 首屏结构和正文应尽量在 JavaScript 执行前显示；
- CSS 和 JavaScript 按需加载并压缩；
- 普通页面避免加载关系图、地图等重模块；
- 图片采用 WebP、AVIF 或优化后的 SVG；
- 图片提供尺寸，避免页面跳动；
- 大图使用响应式资源；
- 不将 PSD、工程源文件、无压缩视频放入发布仓库；
- 持续监控 Pagefind 索引规模，避免一次加载全部正文 JSON；
- 常规 CI 构建目标控制在 5 分钟内。

建议代表页面目标：

- Lighthouse Performance：桌面不低于 90；
- Lighthouse Accessibility：不低于 95；
- Lighthouse Best Practices：不低于 95；
- 页面无明显横向溢出和布局跳动。

## 13. 安全与内容边界

GitHub Pages 输出的是公开静态文件。任何进入 `public/` 的内容都视为已经公开。

要求：

- 内部设定与公开 Wiki 分库或通过明确的内容导出流程隔离；
- 不提交账号、Token、密钥或个人隐私信息；
- 外部脚本和依赖尽量减少；
- 第三方资源必须经过审核；
- `unsafe` HTML 默认关闭；
- 用户可控内容不得直接拼接为 HTML；
- GitHub Actions 依赖版本需定期更新和审查。

世界内的“机密”“限制访问”只是叙事表现，不是真实权限控制。

## 15. 内容工作流要求

### 15.1 角色

- **世界观负责人**：决定设定是否成立、实体归类和冲突处理。
- **内容编辑**：录入、整理、校对和建立链接。
- **内容审核**：检查事实一致性、剧透和公开边界。
- **前端负责人**：模板、组件、样式、交互和可访问性。
- **技术维护者**：构建、部署、校验脚本和依赖升级。
- **发布负责人**：批准合并和正式上线。

一个人可以兼任多个角色，但职责必须明确。

### 15.2 基本流程

```text
建立 Issue 或编辑任务
→ 创建分支
→ 新建或修改 Markdown
→ 本地预览
→ 执行构建检查
→ 提交 Pull Request
→ 内容审核
→ 技术检查
→ 合并 main
→ GitHub Actions 自动部署
→ 线上抽查
```

## 16. 验收标准

### 16.1 内容与结构

- 所有独立实体具有稳定 ID；
- 不存在重复 ID；
- 必填字段完整；
- 页面归类明确；
- 重要条目至少能通过目录与搜索两种方式找到；
- 大型实体可以拥有子页面；
- 重命名不会破坏内部关系。

### 16.2 浏览与交互

- 首页、门户、列表和详情页正常；
- 面包屑和页面目录正确；
- 分类页正常；
- 搜索支持标题、正文、ID 和馆藏编号；
- 手机宽度无阻断性问题；
- JavaScript 关闭时核心正文仍可读。

### 16.3 工程质量

- 本地构建无错误；
- CI 检查通过后才允许合并；
- 主分支自动部署；
- 部署可追溯到提交；
- 构建失败不会覆盖线上稳定版本；
- 可以通过回退提交恢复上一版本。

### 16.4 设计质量

- 用户能在 10 秒内识别页面标题、类型和主要操作；
- 正文适合长时间阅读；
- 图书馆叙事不妨碍功能；
- 键盘导航和焦点状态完整；
- 代表页面可访问性达到既定指标。

## 19. 完成定义

一个功能只有在同时满足以下条件后才算完成：

1. 功能实现并能在本地运行；
2. 移动端与桌面端均可使用；
3. 内容编辑者知道如何使用；
4. 失败和空状态已经处理；
5. 不破坏无 JavaScript 的基本阅读；
6. 已通过代码或内容审核；
7. 已在 GitHub Pages 环境验证；
8. 相关维护文档已经更新。
